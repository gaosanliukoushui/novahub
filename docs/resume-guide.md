# NovaHub 简历与面试写法

## 1. 写进简历前，先定项目定位

NovaHub 最适合的定位不是“社交平台练手项目”，而是：

- 全栈作品
- 高并发社区后端作品
- 可演示、可验证、可讲架构的工程化项目

简历上不要弱化它的工程部分。真正能拉开差距的不是页面多漂亮，而是你能不能把下面这些讲清楚：

- 为什么用 Redis
- 为什么做幂等和限流
- 为什么热榜要有 Redis 和数据库双层
- 为什么写链路要加 outbox
- 为什么要补 Docker、smoke、压测、traceId

## 2. 项目标题怎么写

推荐写法：

`NovaHub 内容社区系统 | Spring Boot / Redis / Kafka / Elasticsearch / Docker`

如果你投全栈岗，可以写：

`NovaHub 全栈内容社区作品 | Java + Redis + Kafka + Elasticsearch + 静态 SPA`

## 3. 项目描述怎么写

### 3.1 标准版

NovaHub 是一个基于 Spring Boot 3、MyBatis-Plus、Redis、Kafka、Elasticsearch、MySQL 构建的内容社区系统，覆盖用户、内容、互动、Feed、热榜、搜索、推荐、通知和监控等模块，并通过 Docker Compose、演示数据、管理接口、自动化测试与压测报告形成可复现的工程化演示闭环。

### 3.2 偏后端版

负责设计并实现内容社区后端核心链路，完成内容发布、点赞收藏评论、Feed 分发、热榜计算、搜索索引同步与推荐曝光点击埋点；结合 Redis 缓存、限流、幂等、Redis ZSet、Caffeine、本地快照回落、outbox 可靠事件和 JMeter 压测，提升系统在热点读写场景下的稳定性与可讲深度。

### 3.3 偏全栈版

独立完成 NovaHub 内容社区全栈实现，后端基于 Spring Boot 多模块架构实现用户、内容、互动、热榜、搜索、推荐与管理能力，前端使用无 Node 构建依赖的静态 SPA 实现首页、详情、评论、用户中心、Dashboard 和 Admin 页，并通过 Docker 一键启动保证演示稳定。

## 4. 三条最推荐的简历 bullet

### 方案 A：综合最强

- 设计并实现多模块内容社区系统，完成注册登录、内容发布、草稿审核、点赞收藏评论、Feed 流、热榜、搜索、推荐、通知和运营看板等核心业务链路。
- 针对高频读写场景引入 Redis 缓存、滑动窗口限流、接口幂等、Redis ZSet 热榜、Caffeine 本地缓存和数据库快照回落，并通过 outbox 可靠事件解耦主事务与异步投递。
- 搭建 Docker Compose 一键部署环境，补充前端 SPA、演示数据、管理运维接口、smoke 脚本、集成测试和 JMeter 压测报告，使项目具备可复现、可验证、可演示的工程化质量。

### 方案 B：偏后端高并发

- 基于 Spring Boot 3 + MyBatis-Plus + Redis + Kafka + Elasticsearch 实现内容社区后端，覆盖内容、互动、Feed、热榜、搜索和推荐等典型高并发场景。
- 设计热榜系统，使用 Redis ZSet 维护实时热度分数，结合时间衰减公式、Caffeine 本地缓存和 `content_stats` 快照回落，降低热点查询延迟并提升冷启动可用性。
- 在写链路中接入接口幂等、滑动窗口限流、数据库唯一约束和 outbox 事件记录，保证发布、点赞、评论等操作的稳定性与可恢复性。

### 方案 C：偏全栈展示

- 独立完成内容社区项目的前后端闭环实现，前端采用静态 HTML/CSS/JS 构建 SPA，支持首页内容流、详情评论、点赞收藏、用户中心、Dashboard 和 Admin 管理页。
- 后端使用 Spring Boot 多模块架构实现用户认证、内容管理、互动、热榜、搜索和推荐等能力，并通过 Redis、Kafka、Elasticsearch 和 MinIO 组成完整基础设施链路。
- 补充 Docker Compose 一键启动、演示账号与数据初始化、接口文档、健康检查、smoke 验证和压测报告，显著提升项目的展示完成度与可信度。

## 6. 面试官最爱追问什么

### 6.1 为什么要做热榜，而不是直接按点赞数排序

推荐回答：

直接按点赞数排序会让老内容长期霸榜，缺少时效性。NovaHub 的热榜引入了评论、收藏、浏览等多维度权重，并叠加时间衰减，让新内容有机会进入榜单，同时 Redis ZSet 适合做高频分数更新和 TopN 查询。

### 6.2 为什么点赞 / 发布要做幂等

推荐回答：

因为真实环境里会出现用户重复点击、网络重试、前端重复提交、脚本刷接口等情况。NovaHub 在接口层通过 Redis 锁做幂等控制，在数据库层通过唯一约束做兜底，防止重复写入和数据污染。

### 6.3 为什么要做 outbox

推荐回答：

如果业务写库成功，但 Kafka 在那一刻不可用，直接发消息会丢失异步事件。NovaHub 把关键事件先记录到 `event_outbox`，后续由重试任务补投，保证主事务成功后异步链路仍有可恢复能力。

### 6.4 为什么不用 IK，先用 standard analyzer

推荐回答：

因为简历项目更重要的是默认环境稳定可启动。官方 ES 镜像默认没有 IK 插件，直接依赖 IK 容易导致 Docker 启动失败。当前先用 `standard` analyzer 保证索引可建、搜索可演示，后续再扩展为自定义 ES 镜像安装 IK。

### 6.5 为什么前端不用 Vue/React

推荐回答：

项目当前目标是演示稳定、部署简单、降低环境依赖，所以前端采用静态 SPA 方案，不需要 Node 构建链就能开箱即用。这个选择更有利于面试现场和仓库复现。

## 7. 一分钟介绍模板

NovaHub 是我做的一套内容社区系统，后端用 Spring Boot 3 多模块架构实现了用户、内容、互动、Feed、热榜、搜索、推荐和通知链路，基础设施用了 Redis、Kafka、Elasticsearch、MySQL 和 MinIO。这个项目我重点不是做普通 CRUD，而是把社区产品里比较典型的工程问题补齐，比如点赞评论的幂等和限流、Redis ZSet 热榜、内容搜索索引同步、outbox 可靠事件、traceId 排障、Docker 一键部署、smoke 验证和压测报告。前端我也补了静态 SPA，能直接演示首页、详情、评论、Dashboard 和 Admin，所以它既能展示业务闭环，也能展开讲后端工程深度。

## 8. 三分钟讲解顺序

1. 先讲产品闭环。
内容发布、互动、Feed、热榜、搜索、推荐、看板都能跑通。

2. 再讲最能体现技术深度的三条链路。
发布链路、点赞链路、热榜链路。

3. 最后讲工程化。
Docker、演示数据、管理后台、smoke、压测、traceId、测试。

这个顺序比按模块背代码更自然，也更像真实做过项目的人。

## 9. 什么不要写

不要写成下面这种弱表达：

- 做了一个类似小红书的项目
- 实现了登录注册增删改查
- 用了很多中间件

这种写法信息量太低，面试官看不出你的技术判断。
